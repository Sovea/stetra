# Change workflow

This document defines the executable Host/CLI workflow for
`cognitive-adoption`, schema `1`. Exact input shapes live in TypeScript schemas
and in the task-specific packets generated by the CLI. This initial protocol
has no translator, alias, dual read/write, or migration path.

## Setup and health

```sh
stetra init .
stetra status .
```

`init` installs project-local Host adapters and records only the artifacts it
owns. Owner-modified generated content is never overwritten without `--force`.
`status` always checks both generated-adapter integrity and Git-worktree
support. It returns `ready` or `needs-attention`; the latter has a nonzero exit
code. There is no separate doctor mode or legacy-installation detector.

## Fixed lifecycle

```text
prepare -> Agent implementation -> collect -> handoff -> decide
                                      |
                                      +-> diagnose -> repair / revision /
                                                       direct review / resolve
```

The lifecycle is fixed. Explicit evidence and Host facts determine which
recovery action is required; Runtime does not infer task meaning or engineering
cause from filenames, dependency counts, diff size, command names, output text,
or a scalar score.

The commands are:

```sh
stetra input reserve . --kind prepare --json
stetra input schema . --kind prepare --json
stetra host begin . --adapter <codex|claude> --binding-token <projected-token> --json
stetra host hook --adapter <codex|claude> --event <session-start|stop> --json
stetra change prepare . --prepare-request <returned-prepare-request-id> --input <returned-owned-input-path> --json
stetra change resume . --prepare-request <returned-prepare-request-id> --json
stetra change collect . --task <task-id> --json
stetra change diagnose . --task <task-id> --input <projected-owned-input-path> --json
stetra change revise-verification . --task <task-id> --input <projected-owned-input-path> --json
stetra change handoff . --task <task-id> --input <projected-owned-input-path> --json
stetra change decide . --task <task-id> --input <projected-owned-input-path> --json
stetra change resolve . --task <task-id> --input <projected-owned-input-path> --json
stetra change guard-final . --task <task-id> --json
stetra change explain . --task <task-id> --section index --json
```

Task state is derived from immutable artifacts and ordered events. It is not a
mutable status machine. Delivery, evidence, and Human decision remain separate
views; `handoff-ready` never means adopted.

## Dynamic Host Projection

Every stage derives a compact structured `hostAction` containing:

- an action kind;
- an exact argv command when the action is executable;
- the smallest generated workflow reference needed for that stage;
- an exact owned-file input binding and Authoring Projection fingerprint when
  Agent or Human input is required.

An Authoring Projection binds the current task, revision, Contract, Attempt,
and Fact Collection. The default Host Action carries only its exact binding and
fingerprint. A Thin Host reserves one editable Draft plus one companion Guide;
the Guide contains bounded semantic context, exact reference catalogs,
task-specific constraints, an exact on-demand schema command, and only
current-action detail commands. The full JSON Schema is generated from the same
validation source through explicit inspection instead of being duplicated into
every Guide. The Guide and executable Host Action use the same exact CLI stage
binding; semantic input names are never reused as guessed command verbs. There
is no separately maintained partial field-rule description that can drift from
validation. Runtime supplies boilerplate identity; the Agent supplies
interpretation and judgment. Prepare transport identity is bound only by the
exact submit command, not by an editable Draft field. Handoff fixes readable
Condition and Obligation keys as task-specific object properties, and Review
Decisions declare targets once; CLI resolves them to canonical IDs and reverse
references before persistence. Draft, Guide, and Schema are transient
projection, not authority, an artifact, or lifecycle state.

Handoff input is task-specific. It fixes Condition and Obligation order and
keys, removes conclusions that unavailable evidence paths cannot support, and
requires every partial, contradicted, or unknown finding to reference a shared
`reviewDecisions` entry. Adoption-critical Conditions always reference one even
when supported, and residual unknowns do the same. A Review Decision explicitly
selects the Conditions and Obligations it covers and supplies one question,
adoption impact, next action, and evidence set. Runtime validates identity and
coverage; it never groups prose by similarity or infers review importance from
files, terms, dependencies, or diff size.

Successful control-plane responses contain counts, status distributions,
fingerprints, exact transition identities, detail commands, and the next exact
action. They never inline an Authoring Projection, full Contract, Fact Bundle,
Patch, Check Attempt history, or Decision Packet. Canonical
detail remains available through identity-bearing `change explain` selectors.
Aggregate views are mechanically size-bounded; exact Contract components,
Baseline paths, Changed Files, Check Attempts, and Evidence Dispositions are
selected individually, and logs require an explicit bounded
tail. No command expands the complete Baseline
tree or Attempt history into one Host response. Compact consumption never
deletes or weakens the persisted Fact Spine.

Input-bearing actions expose one owned-file binding. The Host runs the exact
reservation command, which
pre-fills the Draft and writes its Guide at exact `.stetra/inbox/` paths; it
reads the Guide once, edits the Draft, and starts the exact argv.
Runtime accepts only a regular file beneath that owned directory, caps it at
8 MiB, and claims each Draft generation once. A successful submission deletes
the Draft and Guide. A typed JSON or schema rejection reissues the same bounded
content at the same owned path with an exact retry command. A valid Prepare
result that creates no Task does the same and retains its `prepareRequestId` and
deterministic Task identity. Each reissued generation remains one-shot. The
inbox is ignored workflow transport: it is neither task state nor authority and
is excluded from worktree facts. Every task-bound transport token contains an
exact deterministic Task prefix. A successful Task transition invalidates all
older Draft and Guide generations for that Task, including an unsubmitted
Handoff Draft made stale by recollection.

Repeated generated-reference names mean keep that reference available. A Host
with continuous context need not reread an unchanged page.

## Host continuity Hooks

`stetra init` installs bounded `SessionStart` and `Stop` Hook groups for the
selected Codex and Claude adapters. The developer must review and trust the
project Hook through the Host's own trust surface. A configured Hook is not
evidence that it ran and never upgrades `hostEnvironment` to an attested native
integration.

Session start hashes the exact Host session identity and returns one exact
`stetra host begin` argv. The begin command consumes its one-time token,
pre-fills the normal Prepare Draft, and binds that session to the deterministic
Task identity for the Prepare request. If Prepare needs clarification or has not
yet created the Task, its owned Draft is reissued under that same binding and
Stop returns the exact pending Prepare transport. The Host does not call begin
again or reserve a distinct Prepare request. Once the Task exists, Stop calls
the same current-fact `guard-final` path.

The ignored `.stetra/host-sessions/` index contains routing identity and
delivered Action fingerprints only. It contains no prompt, transcript, Contract,
fact, Handoff, or decision. The bridge does not scan `.stetra/tasks/`, choose a
recent Task, inspect Agent prose, or infer meaning from repository changes.
One unchanged Action fingerprint can force only one continuation in one Host
session. A new fingerprint can force one new continuation; a repeated pending
Action becomes a visible warning rather than an infinite Stop loop.
Presenting a current Developer Decision Brief is different: it is the intended
end of the Agent turn, so Stop surfaces one non-blocking reminder and returns
control to the developer without requesting another Agent response.

Hooks are continuity support, not a prerequisite for the portable workflow. If
SessionStart projects no command, the Host may begin through
`stetra input reserve . --kind prepare --json` and the exact `submit.argv`
returned with that bounded Draft. It must not invoke `stetra host begin`
without the projected adapter and one-time binding token or reconstruct either
value. The Hook-independent path has no Host-session continuity claim; later
actions still follow their exact task-scoped `hostAction`.

Hook configuration is a Stetra-owned JSON fragment rather than an owned file.
Initialization preserves other tools' Hook groups and JSONC comments. Drift in
the Stetra groups blocks replacement unless `--force` is explicit. Hooks guard
workflow continuity only: they do not run checks outside `change collect`,
dispatch an Independent Challenger, attest Host policy, or decide adoption.

Machine-readable `hostEnvironment` disclosure states that the generated
adapter is a Thin Skill and Independent Challenge execution is unavailable. It
also makes the verification boundary
explicit: Runtime owns frozen argv execution during `change collect`; direct
Host runs are Agent evidence only; Prepare preflight checks only the top-level
executable. The disclosure is transient projection, not task authority or
persisted state.

## Prepare: compile the Semantic Contract

Prepare input supplies:

- one or more exact developer messages;
- an Agent interpretation of desired outcome, constraints, non-goals, and focus;
- every exact Human Event and the explicitly selected Repository-evidence basis
  for the task interpretation;
- unresolved or resolved material decision forks;
- one explicit assurance declaration: either basis-bearing `routine` with a
  concrete rationale, or `conditioned` with one or more Adoption Conditions and
  falsifiable Evidence Obligations;
- explicit Host-policy requirements;
- an explicit `verification.mode` containing commands or a concrete no-command
  rationale; and
- an optional `executionBudgetOverride`; otherwise CLI binds the deterministic
  default Check, delivery-repair, and timeout-retry budgets.

A bounded timeout retry must permit a strictly longer attempt than the initial
Check budget; equal durations are rejected because they add no execution
opportunity. Timeout remains an operational budget, not Check identity.

Focus paths guide investigation and review. They are not write permissions or a
prediction of the final changed files.

The generated Prepare Draft is intentionally incomplete and contains no fake
verification executable. The Agent must fill exact developer content and task
meaning, make the assurance choice, and either add repository-valid Check argv
or provide a concrete no-command rationale before submission.

Routine work has no Condition only through an explicit `routine` declaration.
Every declared Condition has at least one
independently concludable Evidence Obligation. Each Obligation freezes:

```text
bounded statement
plausible failure hypothesis
concrete scenario
supporting observation
contradicting observation
explicit evidence strategies
```

Strategies are Runtime Check, bounded Repository Evidence, or Independent
Challenge. Direct Human review is not authored as a strategy that can make the
evidence path complete. It is a review consequence when required evidence is
missing, unavailable, unverified, or adverse.

An adoption-critical Condition always requires direct Human review, but it does
not fabricate an Independent Challenge requirement when no trusted Host
execution boundary exists. An explicitly declared `required` Challenge is
always required. An explicitly declared `fact-triggered` Challenge applies
whenever the Obligation relies on a declared verifier acceptance surface changed
by the implementation. Runtime follows only exact Obligation, Verifier,
Definition, selector, and changed-path relationships.

Each Check freezes ordered preparation commands, one assertion command,
declared ignored execution inputs, baseline policy, and explicit verifier
selectors. Every Check is one isolated preparation-to-assertion pipeline:
preparation establishes only that Check's preconditions, and no Check may rely
on files or side effects produced by another Check. Preparation cannot itself
provide a passing Check. `file` selectors match one exact path; `tree`
selectors match a root and descendants. There are no globs or framework
filename rules.
Commands remain argv-only. Exact developer content must use stdin or another
argument-safe interface rather than shell interpolation. Required ignored or
generated artifacts belong in explicit preparation commands.

A `task-start` baseline is allowed only when before/current comparison changes
a named Evidence Obligation. The Agent supplies its rationale and expected
baseline/current statuses. CLI derives the exact Obligation bindings from the
Obligations that already select that Check, removing a duplicate
cross-reference. Otherwise use `{ "mode": "unknown" }`. The Git baseline and a
baseline Check observation remain different facts.

Repository Evidence is an exact UTF-8 line range. `wholeFile: true` is resolved
before Core compilation into text, line boundaries, and digest. Empty files are
rejected rather than assigned an invented line.

Material decision forks describe only a choice that changes task meaning,
public behavior, compatibility, ownership, a long-lived tradeoff, an external
effect, verification relaxation, or an exception. An unresolved fork produces
one consolidated clarification brief and creates no task. A later exact
developer message resolves it. Another planning framework may own the
conversation and submit the already resolved result once; Stetra does not run a
second generic clarification dialogue.

`prepareRequestId` gives one concrete submission transport identity. Thin Host
reservation generates it, binds it only in the exact submit and resume commands,
and leaves it out of the editable Draft. Exact replay returns the existing task
without rerunning baseline checks; different input under the same ID is
rejected. `change resume` performs only an exact lookup by this identity and
writes no state. Runtime never deduplicates by semantic similarity or chooses a
recent task.

Prepare captures the complete dirty and non-ignored untracked Git baseline,
runs only selected baseline Checks, includes their side effects in the frozen
baseline, and publishes a task only after all initial artifacts are complete.

## Implement and collect: build the Fact Spine

The Agent performs necessary local, reversible engineering work within the
compiled task meaning. Collection then executes every frozen Definition
without a shell and records the baseline-to-current change.

```sh
stetra change collect . --task <task-id> --json
stetra change collect . --task <task-id> --timeout-ms 600000 --json
stetra change collect . --task <task-id> --refresh --json
stetra change collect . --task <task-id> \
  --retry-check '<definition-id>=900000' --json
```

Runtime records:

- complete file operations, kinds, modes, digests, and representable patch;
- pre-check, post-check, and check-induced worktree changes;
- exact preparation/assertion attempts and execution-input snapshots;
- duration, timeout budget, structured termination, bounded stdout/stderr,
  complete-stream digests, and outcome fingerprint;
- mechanical baseline/current relations and evidence concerns;
- exact verifier mutations; and
- platform, architecture, and resolved top-level executables.

The environment observation deliberately excludes guessed toolchain,
dependency, lockfile, environment-variable, and executable-version facts.
Those require explicit future consumers and trustworthy collection.

A passing Check is one machine fact about one Definition. It is not a semantic
conclusion. Completed failure, signal, timeout, and spawn failure remain
distinct.

If current facts still match the worktree, ordinary Collect returns them without
rerunning commands or writing state. `--refresh` explicitly replaces the full
current observation. A timeout retry may append only after an actual timeout,
with unchanged facts and a larger budget; it never hides the earlier attempt.
Its maximum duration and maximum retry count are frozen at Prepare. The count
is task-wide per logical Verifier, so delivery repair or Definition revision
cannot silently reset the operational retry budget.

## Diagnose and recover

Every current non-passing Check and baseline-expectation mismatch must be
diagnosed explicitly. The task-specific draft contains every
current concern exactly once. For each concern, the Agent declares:

- cause: `implementation`, `environment`, `verification`, or `unknown`;
- a fact-bound diagnosis and falsification attempt;
- whether a repository edit can alter the observation;
- one stable repository-change object containing a production,
  verifier-surface, or no-change surface plus an intended-change array (empty
  only for no change); and
- the observation expected from the next Attempt.

Runtime validates exact sources, complete coverage, change-surface consistency,
and route compatibility. It does not parse error prose to choose a cause.

```text
implementation -> bounded delivery repair or handoff
environment    -> verification revision, handoff, or Human resolution
verification   -> delivery repair for repository verifier content,
                  otherwise verification revision, handoff, or Human resolution
unknown        -> handoff or Human resolution
material semantic impact -> exact Human resolution
```

A proposed route is Agent judgment. Runtime still derives the actual successor:
an unavailable required Challenge remains a Handoff and direct-review gap.
Delivery repair creates a lineage-linked successor Attempt and is bounded by
`maxDeliveryRepairs`. Exhaustion remains visible and routes to Handoff.

### Verification Revision

`execution-rebinding` changes only executable commands and retains the rest of
each Check definition. `verification-plan` may change broader verification
meaning. Removing a Verifier, task-start baseline, Obligation binding, or
verifier surface requires an exact developer authorization event plus a
separate Agent interpretation of that authorization.

Revision preserves semantic identity, creates new Verification Plan and
effective identities, gives changed Definitions new identities, retains every
old fact, and creates a successor Attempt. If the original baseline cannot be
honestly reconstructed, it becomes `baseline-unknown-after-revision`; the
modified worktree is never relabeled as the original baseline.

### Human Resolution

`change resolve` records an exact mid-task developer message and a separate
interpretation bound to the pending target. It handles semantic impact,
Host-policy gaps, and correction continuation. All current required Host-policy
gaps produced by the same thin Host boundary share one resolution target and
one exact Human Event while retaining every requirement identity. A recorded
resolution is part of the final Decision Packet and compact developer brief when
it affects the task.

The projected `resolve-evidence-decision` action is a Human stop, not an
Agent-executable authoring action. Its top level exposes the exact pending target
and available Human actions but no command or input binding. The exact
`change resolve` binding exists only under a `resolutionContinuation` marked
`requiresNewHumanEvent: true`. The Host presents the target and stops; only a
later developer message may supply the Human Event and authorize use of that
continuation. A thin instruction-only adapter cannot cryptographically attest
message authorship, so it states this limitation honestly and never permits an
earlier task event to be relabelled as the new resolution.

## Independent Challenge

Independent Challenge remains an explicit evidence strategy, but the current
generated adapters cannot prove fresh-context execution. Stetra therefore does
not expose a Challenge command, install a Challenger profile, launch a provider
process, or accept Agent-authored context identity as attestation.

When a required or fact-triggered Challenge has no trustworthy execution
surface, the current action is a direct bounded Handoff. The related evidence
path remains missing, the conclusion is capped, Agent acceptance advice is
blocked, and the frozen failure hypothesis becomes a concrete developer review
decision. No Human event or same-context Agent assertion may claim that the
independent observation occurred.

A future Host integration may supply independent evidence only through a
narrow, provider-neutral capability port backed by a control plane that
actually owns the relevant context and source-snapshot boundary. That future
port is not part of the current CLI lifecycle.

## Cognitive Handoff

Handoff is authored only after complete current facts exist. Its first-class
actual-change model states:

```text
actual behavior
implementation mechanism
preserved invariants
failure and recovery behavior
important effects
material tradeoffs
```

Its input identifies Conditions and Obligations by their frozen readable keys;
Runtime resolves those keys to exact canonical IDs and rejects unknown keys.
It then concludes every Evidence Obligation and Condition exactly once, records
the falsification attempt and observed result, preserves counterevidence and
coverage gaps, lists residual unknowns with one explicit task, Condition, or
Obligation target, asks only consequence-directed review
questions, and gives an Agent recommendation.

Runtime prevents a conclusion from exceeding its Obligation findings or
declared evidence coverage. Missing, unavailable, or unverified evidence paths
remain separate from the Agent's semantic finding. They add Attention, block an
Agent `accept` recommendation where applicable, and require direct review; they
do not become semantic contradictions merely because a Host boundary was
unavailable.

The Developer Decision Brief never presents a bare Condition conclusion. Each
status is locally qualified as Agent judgment over declared evidence, with
Independent Challenge explicitly not attested by the current thin Host. This
does not rewrite `supported` to `partial`; missing independent evidence remains
a separate evidence-path and review issue.

Edits after collection return `facts-stale` before Handoff validation.

The explicit `decision-packet` detail contains one canonical packet:

- exact Human Events and Human resolutions;
- compact Semantic Contract;
- the actual-change model and Agent recommendation;
- Condition and Obligation findings beside evidence-path states;
- residual unknowns, Attention, and shared Review Decisions;
- compact Runtime change and Check facts; and
- named detail sections for exact artifacts.

The transient `developerDecisionBrief.primary` is the concise Human surface. It
uses semantic statements rather than opaque IDs, leads with the four separate
delivery/evidence/recommendation/adoption states, explains the actual change,
summarizes each Condition's findings and evidence-path state, consolidates only
structurally identical blockers, directs review, and asks for the pending Human
decision. `developerDecisionBrief.details.command` retrieves the canonical
Decision Packet only when deeper evidence boundaries, exact IDs, or history
are needed; it does not duplicate them
in the primary surface.

## Decide and correct

After Handoff, the decision command appears only under
`hostAction.decisionContinuation` with `requiresNewHumanEvent: true`. The Host
presents the brief, states that adoption is pending, asks the developer, and
stops. It asks in plain text rather than invoking an interactive input tool.
Only a later exact developer message authorizes `change decide`.

Actions are `accepted`, `correction-requested`, `rejected`, and `deferred`.
Acceptance with Attention must name every current Attention ID and provide a
rationale. Decide never commits, merges, publishes, deploys, or activates
cross-task state.

`correction-requested` is not terminal. A later exact Human Resolution creates
a `correction` successor Attempt under the current or newly compiled contract,
while prior Handoff, Decision, facts, and events remain immutable.

## Final-response guard and inspection

Immediately before a Host final response, `change guard-final` rereads task and
worktree state without mutation. It returns:

- `continue-workflow` with the current required action;
- `present-decision-brief` with the current brief; or
- `human-decision-recorded`.

An exact known action fingerprint allows the Host to reuse only that unchanged
action. A mismatch returns the complete current action. The generated Codex and
Claude Stop Hooks provide bounded exact-session continuation without claiming
native attestation.

Every task-bound `hostAction` also includes the exact
`finalResponseGuard.argv`. The Agent invokes that command directly before its
final response. It never invokes `stetra host hook` manually; provider Hooks are
only an automatic continuity backstop.

Inspection is deliberately sectional:

```text
index | action | action-input | contract | baseline | attempts |
revision | handoff | decision-packet | decision | events
```

`index` is the default and expands no canonical artifact. `action-input`
requires an exact current stage and exposes one explicit `draft`, `guide`, or
`schema` part; `handoff` is the persisted Cognitive Handoff and evaluation.
Unsupported sections fail.

Schema-invalid structured input returns a transient correction packet with the
submitted fingerprint, exact issue paths, bounded local previews, and an exact
retry when an owned file was reissued. It writes no task state and never echoes
the full document. Malformed JSON is represented as one root structural issue;
the Runtime does not parse engine-specific error prose. `change resume` only
recovers a Task that may already have been published. It does not replace the
reissued Draft, repeat `host begin`, or create a new Prepare request.

## Persistence and transactions

Task state lives under `.stetra/tasks/<taskId>/`. `events.jsonl` is the
append-only lifecycle source; `task.json` is a rebuildable projection. The
projection stores immutable identities, not artifact paths that can be derived
from those identities. Contracts, baselines, Attempts, Fact Bundles, evidence
dispositions, Verification Revisions, Handoffs, Human Resolutions,
and Decisions are immutable.

Prepare and Collect hold a project-worktree lease while observing or running
checks, stage complete artifacts, then hold a short task commit lock while
comparing revision and publishing. A lease is reclaimed only when its owning
process is confirmed dead; elapsed time is never sufficient. Conflicting
writers fail rather than overwrite a newer projection.
